## Overview

Users want mobile and desktop access to the Update Analysis dashboard with push notifications for new updates. Rather than building separate native apps, we take a **two-phase approach**:

- **Phase 1 (PWA):** Ship a Progressive Web App — installable on mobile and desktop from the browser, with push notifications via the Web Push API. No app store needed. This is the demo launch target.
- **Phase 2 (Capacitor):** If iOS notification reliability becomes an issue, wrap the existing Next.js app in a Capacitor native shell for native APNs and optional App Store/TestFlight distribution.
- **Phase 3 (React Native):** Build a fully native mobile app with React Native — native UI, full device API access, App Store/Play Store presence. Long-term investment in native mobile experience and team capability building.

### Why PWA First?

- Zero deployment friction — users install from the browser, no app store review
- Same codebase, same URL, same Vercel deployment
- Works on Android, iOS (16.4+), Windows, Mac, and Linux
- Push notifications work natively on Android and desktop; iOS requires the app to be installed to home screen first
- Desktop "Install App" support in Chrome/Edge comes free with the PWA manifest

### Service Worker Setup

Use `@serwist/next` (actively maintained successor to `next-pwa`):

```bash
npm install @serwist/next @serwist/sw
```

The service worker handles two concerns:

1. **Caching** — cache app shell and static assets for offline/fast loading
2. **Push events** — listen for incoming push messages and display notifications

### Push Notification Flow

```
1. New row inserted into rdn_new_updates
          │
          ▼
2. Supabase Database Webhook fires
   (configured to trigger on INSERT)
          │
          ▼
3. Supabase Edge Function receives webhook payload
   - Reads push_subscriptions table for all active subscriptions
   - Formats notification payload (title, body, URL)
   - Sends Web Push request to each subscription endpoint
          │
          ▼
4. Browser push service (FCM/APNs/Mozilla) delivers to device
          │
          ▼
5. Service worker 'push' event fires
   - Displays system notification with update details
   - Click opens /updates in the app
```

### Subscription Storage — `push_subscriptions` Table

```sql
create table push_subscriptions (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references auth.users(id) on delete cascade,
  endpoint text not null,
  p256dh text not null,
  auth_key text not null,
  user_agent text,
  created_at timestamptz default now(),
  unique(user_id, endpoint)
);

-- RLS: users can only manage their own subscriptions
alter table push_subscriptions enable row level security;

create policy "Users manage own subscriptions"
  on push_subscriptions for all
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);
```

### Desktop Install

No extra work needed beyond the manifest. Chrome and Edge automatically show an "Install" icon in the address bar when a valid `manifest.json` is detected and a service worker is registered. The installed app:

- Opens in its own window (no browser chrome)
- Gets a taskbar/dock icon
- Uses `theme_color` for the title bar
- Launches from `start_url` (`/updates`)

### iOS Limitations

- Push notifications require **iOS 16.4+** and the PWA must be **installed to the home screen** (not just opened in Safari)
- There is no install prompt on iOS — users must manually use Safari's "Add to Home Screen" action
- Background push delivery can be less reliable than native APNs
- No badging API support on iOS

These limitations are the primary trigger for Phase 2 (Capacitor) if they become a problem for real users.

### What You Gain

| Capability | PWA | Capacitor |
|-----------|-----|-----------|

- **Entire web codebase** — Capacitor loads the same Next.js app in a native WebView

### Migration Steps (When the Time Comes)

1. `npm install @capacitor/core @capacitor/cli`
2. `npx cap init` — generates `capacitor.config.ts`
3. `npx cap add ios && npx cap add android`
4. Configure `server.url` to point to the Vercel deployment (live reload) or bundle the static export
5. Replace Web Push with `@capacitor/push-notifications` plugin for native APNs/FCM
6. Build and distribute via Xcode (TestFlight) and Android Studio (Play Store)

### What Stays the Same

- **Supabase integration** — `@supabase/supabase-js` works in React Native; same queries, same auth
- **Data layer / business logic** — query functions from `lib/queries.ts` can be reused directly
- **Push notification backend** — same Edge Function, same `push_subscriptions` table (swap Web Push endpoint for FCM/APNs device tokens)
- **Auth flow** — same `supabase.auth.signInWithPassword()`, stored via `@react-native-async-storage/async-storage`

### What Needs to Be Rebuilt

- **UI components** — React Native uses `<View>`, `<Text>`, `<ScrollView>` instead of HTML/CSS. The dashboard layout, cards, sidebar, charts, and navigation all need native equivalents
- **Styling** — move from Tailwind CSS to React Native StyleSheet or NativeWind (Tailwind for React Native)
- **Navigation** — replace Next.js routing with React Navigation (`@react-navigation/native`)
- **Charts** — replace any web chart library with a React Native option (`react-native-chart-kit` or `victory-native`)

We'll build this hands-on with **Expo (managed workflow)** and **Claude Code** — no no-code platforms, full control over every line of code.

### Why Not No-Code?

Platforms like **Emergent** and similar no-code/low-code mobile builders were considered for Phase 3. They promise faster initial delivery, but we chose Expo + hands-on development for these reasons:

| Concern | No-Code Platform | Expo + Claude Code |
|---------|-------------------|-------------------|
| **Code control** | Generated code you can't fully inspect or modify | You own every line — full visibility and control |
| **Vendor lock-in** | Tied to the platform's runtime and export limitations | Standard React Native — portable to any hosting or build service |
| **Customization ceiling** | Hits a wall when you need custom native modules or complex logic | No ceiling — drop down to native Swift/Kotlin when needed |
| **Debugging** | Limited to platform's debugging tools | Full access to React Native debugger, Flipper, Xcode, Android Studio |
| **Team learning** | Team learns the platform, not the underlying technology | Team builds transferable React Native and Expo expertise |
| **Long-term cost** | Monthly platform fees + potential migration cost if you outgrow it | Free tooling (Expo free tier covers most needs), no platform dependency |

**Bottom line:** No-code is great for prototyping, but for a production app we'll maintain long-term, full code ownership matters more than speed-to-first-build.

## Decision Matrix — PWA vs Capacitor vs React Native

| Factor | PWA | Capacitor | React Native |
|--------|-----|-----------|--------------|
| **Development effort** | Low — add manifest + service worker to existing app | Medium — wrap existing app in native shell | High — rewrite UI in React Native components |
| **Codebase reuse** | 100% — same Next.js app | ~95% — same web app, thin native layer | ~30% — shared logic only, new UI layer |
| **Push notifications** | Web Push (reliable on Android/desktop, caveats on iOS) | Native APNs + FCM (fully reliable) | Native APNs + FCM (fully reliable) |
| **App Store distribution** | No | Yes | Yes |
| **Offline support** | Service worker caching | Service worker + native fallbacks | Native storage |
| **Update deployment** | Instant — just deploy to Vercel | Instant for web content, App Store review for native changes | App Store review for all changes |
| **Time to ship** | Days | 1–2 weeks | Months |
| **Maintenance burden** | Minimal — it's the same web app | Low — thin native wrapper | High — separate UI codebase |

### Why This Phased Approach

1. **PWA first (Phase 1)** — fastest to ship, no app store friction, same deployment pipeline. Good enough for demo launch
2. **Capacitor if needed (Phase 2)** — solves iOS push reliability with minimal effort by wrapping the existing web app
3. **React Native long-term (Phase 3)** — fully native experience, App Store presence, and builds internal mobile development expertise for future products
4. **Each phase builds on the last** — PWA validates the mobile use case, Capacitor proves app store viability, React Native delivers the polished native product
